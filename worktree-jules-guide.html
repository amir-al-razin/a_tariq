Concept First
What is Git Worktree — and Why You Need It
Before the steps, you need to understand this. It changes how you think about your repo.
🌳

Git Worktree — Plain English

One Git repo. Multiple folders on your disk. Each folder is a different branch. All live at the same time.

❌ Without Worktree

Normal Git (one folder)

You have one folder for your repo. To review Jules PR #7, you must git stash your current work, git checkout feat/issue-07, look at it, then switch back. Repeat 15 times = misery.

→
✅ With Worktree

Multiple folders, one repo

You have 15 folders simultaneously — one per Jules PR. Each is a clean checkout. Open any folder in your IDE and review it. Your main working folder is never touched.

The key insight: A worktree is not a clone. It's the same repo — same .git database — but Git checks out a different branch into a different physical folder. Changes in one don't affect the others. You can have 15 worktrees open and your disk shows 15 folders, each on a different branch.

How It Fits Your Jules Workflow Exactly
~/projects/ │ ├── my-app/ ← Your MAIN worktree (your normal working folder) │ ├── .git/ ← The ONE shared git database │ ├── .claude/commands/ ← Your existing skill files live here │ ├── scripts/worktree-setup.sh ← Already exists! Creates folders below │ └── ... (branch: main) │ ├── my-app-wt/ ← Worktrees folder (sibling to your repo) │ ├── integration-sprint-1/ ← Jules PRs merge here; you review here │ ├── feat-issue-07/ ← Jules agent #7's PR branch │ ├── feat-issue-12/ ← Jules agent #12's PR branch │ ├── feat-issue-23/ ← Jules agent #23's PR branch │ └── ... up to 15 at once │ └── (no cloning needed — all point to same .git)
💡 Why this matters for 100 tasks/day: Jules opens 15 PRs. Without worktrees you'd need to clone the repo 15 times or constantly switch branches. With worktrees, you cd my-app-wt/feat-issue-07, open it, review it, close it. No stashing, no branch switching, no lost work.

One-Time Configuration Checklist
⚙️ Do Once Per Project

Configure Your worktree-setup.sh

Open scripts/worktree-setup.sh and verify these variables match your setup.

# scripts/worktree-setup.sh — verify / edit these values REPO_ROOT="$(git rev-parse --show-toplevel)" # auto-detected ✓ WT_BASE="${REPO_ROOT}/../my-app-wt" # sibling folder for worktrees INTEGRATION_BRANCH="integration-sprint-1" # update per sprint BASE_BRANCH="main" # your stable base # Creates the integration worktree (where Jules PRs land) git worktree add "${WT_BASE}/integration-sprint-1" "integration-sprint-1" # To add a worktree for a specific Jules PR branch: git worktree add "${WT_BASE}/feat-issue-07" "feat/issue-07"
ℹ️ The branch (feat/issue-07) must already exist in GitHub before you can add a worktree for it. Jules creates it when it opens the PR. After Jules pushes, run git fetch, then add the worktree.
📄 AGENTS.md — Place in Repo Root

Your Universal Rules File (Jules Reads This)

Jules reads AGENTS.md in the repo root automatically. Your .windsurfrules / .cursorrules is for local IDE. Keep both.

# AGENTS.md — place at repo root (Jules reads this natively) ## Execution Rules (Jules must follow) - Before writing any code: read the plan file specified in the task prompt - File scope: only modify files listed in the plan. Touch nothing else. - Branch: always branch from integration-sprint-{N}, never from main - Validation: run all commands listed under "Validation" in the plan before opening PR - If blocked: do not guess. Stop and leave a detailed comment in the PR. - Migrations: if schema changes, run bun run scripts/migrate.ts after code changes - Smoke test: run bun run scripts/smoke.ts as final validation step ## Tech Stack - TypeScript strict mode. No `any` types. - [Add your stack here: Next.js / Hono / Drizzle / etc.] ## Code Style - Functional components only. Named exports. No default exports from components. - All utility functions need a corresponding test in __tests__/

1
🧠 Local IDE — Brainstorm → PRD

Run .claude/commands/prime.md then create-prd.md

Prime your local IDE with project context first, then convert your feature ideas into a structured PRD.

# In your local IDE (Cursor/Windsurf/Copilot — any) # Step 1a: Prime the IDE with project context # → Open .claude/commands/prime.md and run it as a prompt # (This loads your stack, file structure, existing patterns) # Step 1b: Create PRD from your feature ideas # → Open .claude/commands/create-prd.md and run it as a prompt # with your brainstorm text appended # Output lands here: ls .agents/PRDs/ # → my-feature-prd.md # Review it. If sections look wrong, edit the text file. # Do NOT skip review — this feeds everything downstream.
💡 prime.md first, always. Your local IDE has no memory between sessions. Priming it with prime.md gives it your full project context so the PRD and plans it generates are accurate to your actual codebase.
2
🎫 Local IDE — PRD → GitHub Issues

Run create-stories.md → Execute the batch script

Convert the PRD into discrete GitHub issues. Each issue becomes one Jules task.

# Run create-stories.md prompt in local IDE, pointing it at your PRD # Output: a shell script in .agents/stories/ ls .agents/stories/ # → create-sprint-1-issues.sh # Review the script — make sure each issue is self-contained # Then execute it to push issues to GitHub: chmod +x .agents/stories/create-sprint-1-issues.sh bash .agents/stories/create-sprint-1-issues.sh # Verify issues appeared: gh issue list # Create the sprint integration branch: git checkout main git checkout -b integration-sprint-1 git push -u origin integration-sprint-1
⚠️ Check dependencies before continuing. If Issue #7 depends on Issue #2 (e.g. needs the DB schema Issue #2 creates), note that. Issue #7 cannot run in parallel with Issue #2 — it must be in the next batch after #2 merges.
3
🗺️ Local IDE — Per-Issue Plans

Run plan.md for each issue in the batch

This is the most important step. The plan is what Jules reads. It must be exact. The IDE reads your actual workspace files to generate it.

# For each issue (do all non-dependent ones before triggering Jules): # Run .claude/commands/plan.md in your IDE, specifying the issue number # Output: docs/plans/issue-07-plan.md # Critical review checklist for each plan.md: # ✓ Files to modify are listed explicitly # ✓ Files NOT to touch are also listed # ✓ No two plans in this batch list the same file # ✓ Validation commands are included # ✓ Branch name matches: feat/issue-[N] # Push all plans to GitHub (Jules will read them from the repo): git add docs/plans/ git commit -m "plans: add sprint-1 issue plans" git push origin integration-sprint-1
⚠️ File conflict check. Before triggering Jules, scan all plans in this batch. If two plans list the same file, pull one out of this batch — run it in the next batch after the first one merges. This is the #1 cause of merge conflicts at scale.
4
🚀 Trigger Jules — All Agents at Once

Fire all Jules tasks in parallel via API or Jules UI

Jules clones the repo into its own VM, reads the plan file, executes, and opens a PR. You do nothing while it runs.

# Option A: Jules UI (easiest for 100/day) # → jules.google.com → New Task × 15 # → Each task prompt: "Read docs/plans/issue-07-plan.md and execute it exactly. Follow all rules in AGENTS.md. Branch from integration-sprint-1. Branch name: feat/issue-07. Open a PR to integration-sprint-1 when done." # Option B: API (for automation / scripting) curl -X POST https://jules.google.com/api/v1/tasks \ -H "Authorization: Bearer $JULES_API_KEY" \ -H "Content-Type: application/json" \ -d '{ "prompt": "Read docs/plans/issue-07-plan.md and execute it exactly. Follow AGENTS.md.", "githubRepoContext": { "repo": "your-org/your-repo", "startingBranch": "integration-sprint-1", "targetBranch": "feat/issue-07" }, "automationMode": "AUTO_CREATE_PR" }' # Repeat this curl for each issue, changing 07 → 08 → 09 etc. # You can fire all 15 in < 2 minutes. Then go do something else.
What Jules Does Inside Its VM (You Don't Touch This)
1
Clones your repo

Spins up a fresh VM. Does a full git clone of your repo into an isolated environment.

2
Reads AGENTS.md and the plan file

Loads your global rules, then reads docs/plans/issue-07-plan.md. This is its entire instruction set.

3
Creates the feature branch

Checks out integration-sprint-1, creates feat/issue-07 from it.

4
Implements the plan

Edits only the files listed in the plan. Writes code, runs npm install if needed.

5
Runs validation commands

Executes every command listed in the plan's Validation section (lint, type-check, tests, smoke.ts).

6
Opens the PR automatically

Pushes feat/issue-07 to GitHub and opens a PR targeting integration-sprint-1. GitHub Actions CI fires immediately.

5
🌳 Worktree — Review PRs Without Branch Switching

Run scripts/worktree-setup.sh → Open worktree folders

This is where Git Worktrees shine. Jules opens 15 PRs. You add a worktree per branch and review each one in its own folder — no stashing, no branch chaos.

# After Jules PRs start arriving, fetch all remote branches: git fetch --all # Run your existing setup script (creates the integration worktree): bash scripts/worktree-setup.sh # For each Jules PR branch you want to review locally, add a worktree: # (Do this once per branch — after Jules pushes, before you review) git worktree add ../my-app-wt/feat-issue-07 feat/issue-07 git worktree add ../my-app-wt/feat-issue-12 feat/issue-12 git worktree add ../my-app-wt/feat-issue-23 feat/issue-23 # ... add as many as needed # List all active worktrees: git worktree list # /home/you/my-app abc1234 [main] # /home/you/my-app-wt/feat-issue-07 def5678 [feat/issue-07] # /home/you/my-app-wt/feat-issue-12 ghi9012 [feat/issue-12] # To review issue-07, just open that folder: cd ../my-app-wt/feat-issue-07 # → Open in your IDE, run the app, check the output # → Your main folder is untouched. Zero context loss.
✅ What You See Per Worktree
  • Clean checkout of that branch's code
  • Can run npm run dev inside it independently
  • Can open in IDE — no branch switch needed
  • Run review.md prompt here for AI-assisted review
  • Changes here don't affect your main folder
🧹 Cleanup After Review
  • After merging a PR, remove its worktree:
  • git worktree remove ../my-app-wt/feat-issue-07
  • Or run your teardown script at end of sprint:
  • bash scripts/worktree-teardown.sh
  • Safe — never deletes branches, just the folder
💡 You don't need a worktree for every PR. If CI is green and the PR diff is small, trust the CI and merge without a local worktree. Use worktrees for complex PRs you want to actually run and test locally.
6
✅ Merge — In Order, With Gates

Traffic-light merge + smoke test every 5

Never merge all 15 at once. Gate every 5 merges with a smoke test. Conflicts go back to Jules — you don't fix them.

# Check PR statuses: gh pr list --base integration-sprint-1 # Merge rule: CI green = merge. CI red = re-trigger Jules. gh pr merge 42 --squash --delete-branch # issue #7 ✓ gh pr merge 43 --squash --delete-branch # issue #8 ✓ # ... after 5 merges: # Sprint gate — smoke test the integration branch: cd ../my-app-wt/integration-sprint-1 git pull origin integration-sprint-1 bun run scripts/smoke.ts # → If smoke fails: stop merging. Find which PR broke it. # → If smoke passes: continue merging next 5. # For a CONFLICTED PR, send Jules a follow-up message: "Pull latest integration-sprint-1, resolve all git conflicts, re-run all validation commands from the plan, push the update." # → Jules handles it. You don't touch the conflict. # For a CI-FAILING PR, re-trigger Jules with: "The CI failed on feat/issue-07. Read the CI error output below, fix the issue, re-run validation, push the fix." # [paste the GitHub Actions error log]
PR Status Your Action Time Cost
CI green, no conflict gh pr merge N --squash 10 seconds
CI failing Paste error to Jules, let it fix 2 min (Jules does it)
Merge conflict Send Jules resolve message 2 min (Jules does it)
Complex — want to run locally Add worktree, npm run dev, review 5–10 min
7
🔍 Sprint Close — Audit + Evolve

Run review.md and validate.md → Update AGENTS.md

After all PRs are merged into the integration branch, audit the result and improve your rules before the next sprint.

# Final validation on the full integration branch: cd ../my-app-wt/integration-sprint-1 git pull origin integration-sprint-1 # Run .claude/commands/validate.md prompt (checks PRD vs delivered code) # Run .claude/commands/review.md prompt (AI-assisted diff review) # If Jules made a systemic mistake (e.g. wrong import style): # → DO NOT just fix the code # → Add a rule to AGENTS.md: # "Always use named imports from '@/lib/utils'. Never use default imports." # Teardown worktrees for this sprint: bash scripts/worktree-teardown.sh # Prepare next sprint: git checkout integration-sprint-1 git checkout -b integration-sprint-2 git push -u origin integration-sprint-2 # Update worktree-setup.sh: change INTEGRATION_BRANCH to sprint-2
💡 Patch the AI, not just the code. Every time Jules makes the same mistake twice, it means your AGENTS.md has a gap. The 3 minutes you spend adding one rule saves hours of repeated manual fixes across 100 future tasks.
