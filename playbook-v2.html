01 — Architecture
The Tripartite Model
Three distinct roles, zero overlap. Separation of concerns is what makes parallel scale possible.
🧠 The Brain

Local IDE

Cursor · Windsurf · Copilot · VS Code · Antigravity · Hero
  • Staff Engineer + PM. Plans but never implements production code.
  • Generates PRD.md, GitHub Issues, and plan.md per task.
  • Produces Jules API trigger scripts.
  • Conducts final audit after each sprint.
⚙️ Assembly Line

GitHub

Issues · Branches · PRs · GitHub Actions CI
  • Single source of truth for all code and work items.
  • Holds the issue backlog generated by the Brain.
  • Runs automated CI tests on every Jules PR.
  • Traffic-light gating: only green PRs get merged.
🤖 The Hands

Jules AI Agents

Cloud execution · 10–15 concurrent workers
  • Triggered via Jules API — remote VMs, zero local load.
  • Reads plan.md and executes it exactly — no deviation.
  • Runs validation commands defined in the plan.
  • Auto-opens a PR on completion.
02 — Parallel Scale
Running 10–15 Agents Safely
The biggest risk at scale is merge conflicts and overlapping file edits. These rules prevent that.
⚡

Compute Arbitrage — Why This Works

Each Jules API call spins up an isolated remote VM in Google's cloud. Your local machine sends 15 small requests and goes idle. Google runs 15 independent agents in parallel, each with their own file system snapshot, running tests, and submitting PRs. You only review the results.

agent-01 → issue-01 agent-02 → issue-02 agent-03 → issue-03 agent-04 → issue-04 …up to agent-15
01

File-Level Task Partitioning

Before triggering Jules, check that no two active issues target the same file. Assign file ownership per issue in AGENTS.md. If two tasks need the same file, serialize them — one after the other, not in parallel.

02

Isolated Feature Branches

Each Jules agent works on its own branch (feat/issue-N) forked from integration-sprint-X. Agents never push to the integration branch directly — only via PR.

03

Merge Order Protocol

Merge PRs in dependency order, not creation order. After each merge, ping conflicted PRs with: "Pull latest integration, resolve conflicts, re-run tests, push." Let Jules fix its own conflicts.

04

Sprint Gate Before Merge Burst

Never merge 15 PRs in one batch without a mid-sprint gate. Merge 5, pull locally, run a smoke test, then continue. This catches cascading breakage early before all 15 PRs land.

03 — Phase 0 Setup
One-Time Repository Bootstrap
Do this once per project. Everything Jules does will be constrained by these files.
📄 AGENTS.md (or .windsurfrules / .cursorrules)

Global AI Constitution

The rules file all agents obey. Name it for your IDE (.cursorrules, .windsurfrules) or use universal AGENTS.md for Jules. Defines tech stack, code style, and execution constraints.

📄 docs/PRD.md

Product Requirements Doc

Generated by the local IDE from your brainstorm. Defines scope, features, technical constraints, and what success looks like. Jules should never need to read this directly — only the plan.

📄 .ai-templates/1-create-prd.md

PRD Generation Prompt

Feed to local IDE to transform your brainstorm into a structured PRD. Instructs AI to act as PM, define scope, and identify tech constraints.

📄 .ai-templates/2-create-stories.md

Issue Generation Prompt

Feed to local IDE to read PRD and output a shell script of gh issue create commands. Creates the GitHub backlog automatically.

📄 .ai-templates/3-plan-task.md

Per-Issue Planning Prompt (Most Important)

Feed to local IDE with a specific issue number. It reads the issue, indexes your workspace, and outputs docs/plans/issue-[N]-plan.md — the exact blueprint Jules will follow. Also generates trigger-jules.sh with the API payload. This is the key hallucination-prevention step.

# AGENTS.md — Universal AI Rules File (works with any IDE + Jules) Tech Stack: Next.js 14, Tailwind CSS, TypeScript, Shadcn UI Code Style: Functional components only. Strict TypeScript. No any types. Naming: PascalCase components, camelCase utils, kebab-case files Testing: Vitest unit tests required for all utility functions # Jules-specific execution constraints Jules Rule 1: Read docs/plans/issue-[N]-plan.md BEFORE writing any code Jules Rule 2: NEVER deviate from the plan. If blocked, stop and comment in PR. Jules Rule 3: Run all validation commands listed in plan before opening PR Jules Rule 4: Branch from integration-sprint-X. Never push to main or integration directly. Jules Rule 5: If a file is not listed in the plan, do not touch it.

04 — Production Loop
The Sprint Workflow
Repeat this loop per sprint. Each sprint should contain 10–15 non-overlapping issues.
1
Ideation & Backlog

Human + Local IDE → GitHub Issues

Brain-dump your feature ideas to the local IDE. It converts them into a PRD, then a GitHub issue backlog via gh issue create commands.

💡 You (Human)
  • Describe the feature set in plain language
  • Run .ai-templates/1-create-prd.md prompt
  • Review and approve docs/PRD.md
  • Run .ai-templates/2-create-stories.md prompt
  • Execute the generated create-issues.sh script
  • Run git checkout -b integration-sprint-1
🧠 Local IDE
  • Acts as PM — extracts scope, constraints, success criteria
  • Generates structured docs/PRD.md
  • Breaks PRD into discrete, independently-completable issues
  • Outputs shell script with gh issue create per issue
  • Flags inter-issue dependencies for serialization
2
Micro-Planning

Local IDE → docs/plans/issue-N-plan.md

For each issue, the local IDE produces a precise implementation blueprint. This is the most important step — it eliminates hallucination by forcing explicit intent before Jules touches a file.

💡 You (Human)
  • For each issue: run .ai-templates/3-plan-task.md with the issue number
  • Review the generated plan.md carefully — if it looks wrong, fix the text, not the code
  • Check that no two parallel plans list the same file
  • Run git add docs/plans/ && git push
🧠 Local IDE
  • Reads the GitHub issue and indexes the workspace
  • Lists exact files to create/modify (and files NOT to touch)
  • Writes step-by-step logic in pseudocode or precise prose
  • Adds validation commands Jules must run before PR
  • Generates trigger-jules.sh API script for this issue
⚠️ Key principle: If the plan looks wrong, fix the text file — not the code after the fact. The plan is your source of truth, not a suggestion.
3
API Delegation

Local IDE → Jules API → 10–15 Parallel Agents

Trigger all issue plans at once. Each Jules agent runs in isolation in the cloud. Your machine does no heavy lifting.

💡 You (Human)
  • Run all trigger-jules.sh scripts (one per issue)
  • Confirm each returns a Jules task ID
  • Open GitHub PRs tab — watch PRs appear as agents complete
  • Do not wait — move to monitoring mode
🤖 Jules AI
  • Receives API payload: plan path + branch + auto-PR flag
  • Clones repo, reads plan.md exclusively
  • Implements changes only on listed files
  • Runs all validation commands
  • Opens PR to integration-sprint-X on success
# trigger-jules.sh — generated by local IDE (one per issue) curl -X POST https://jules.google.com/api/v1/tasks \ -H "Authorization: Bearer $JULES_API_KEY" \ -H "Content-Type: application/json" \ -d '{ "prompt": "Read docs/plans/issue-07-plan.md and execute it exactly. Follow AGENTS.md rules.", "githubRepoContext": { "repo": "your-org/your-repo", "startingBranch": "integration-sprint-1", "targetBranch": "feat/issue-07" }, "automationMode": "AUTO_CREATE_PR" }'
4
CI & Traffic-Light Merge

GitHub Actions → Review → Ordered Merge

GitHub Actions auto-tests each PR. You merge passing ones in dependency order, not creation order. Failing or conflicted PRs go back to Jules.

💡 You (Human)
  • Only merge PRs with green CI — red means Jules needs to retry
  • Merge in dependency order (foundation features first)
  • After every 5 merges: pull locally and run a smoke test
  • For conflicts: send Jules a follow-up message (see below)
🤖 Jules (conflict resolution)
  • Send via Jules :sendMessage endpoint:
  • "Pull latest integration-sprint-1, resolve git conflicts in [file], re-run all validation commands, push update."
  • Jules resolves and re-pushes to the same PR branch
  • CI re-runs automatically
5
🔍 Sprint Audit

Local IDE → Audit → Evolve the System

Pull the integration branch. Local IDE compares the result against the original PRD. Systemic mistakes become rule updates — you patch the AI, not just the code.

💡 You (Human)
  • Pull integration-sprint-1 using a Git Worktree (keeps your working dir clean)
  • Visually review key screens and run the full test suite
  • Note any systemic patterns in Jules' mistakes
  • Update AGENTS.md and plan templates before next sprint
🧠 Local IDE (audit role)
  • Review git history vs docs/PRD.md — what was missed?
  • If Jules used wrong patterns (e.g. CSS instead of Tailwind), add a rule to AGENTS.md
  • Rewrite plan template to add guards against that specific failure
  • Prepare next sprint's integration branch: integration-sprint-2
05 — System Evolution
Patch the AI, Not Just the Code
Every systemic Jules mistake is an opportunity to strengthen your rules. A stronger AGENTS.md means fewer mistakes next sprint.

Jules makes a mistake

e.g. Outputs plain CSS instead of Tailwind. Uses class components instead of functional. Modifies a file outside the plan.

→

❌ Wrong: Fix only the code

You manually patch the CSS. Jules will make the same mistake again in the next sprint.

Root-cause analysis

Ask: Was the rule missing from AGENTS.md? Was the plan template ambiguous? Was the issue description too vague?

→

✅ Right: Fix the instruction

Add a strict rule to AGENTS.md: "Always use Tailwind. Never write raw CSS." Next sprint, Jules never repeats it.
