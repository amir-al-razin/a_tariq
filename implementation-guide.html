01 — Understand First
Your Monorepo — What Each Part Does
Before writing a single line, you need to see the three zones clearly. The bridge between mobile and web is packages/shared.
📱

apps/mobile

Status: Done ✓ — your reference

screens/ ← all your screens components/ ← RN components state/ ← Zustand/context i18n/ ← translations locales/ ← AR/EN strings theme/ ← design tokens App.tsx ← entry point tailwind.config.js
🔗

packages/shared

The Bridge — used by both apps

data/ ← Arabic content chapters, words, exercises, vocab index.ts ← exports everything ↑ THIS is where your Arabic pedagogical data lives. Both mobile and web import from here.
🌐

apps/web

Status: Scaffolded — build this

src/ ← empty shell messages/ ← i18n strings drizzle.config.ts ← DB ready vite.config.ts components.json ← shadcn ↑ Needs: • pages / routes • components • state • RTL support • same features as mobile
💡 Key insight: Your Arabic content data in packages/shared/data/ is the most valuable asset — it took the most work. The web app just needs to consume it differently (browser rendering, Drizzle DB, URL routing instead of React Native navigation). You're not rebuilding the content. You're rebuilding the container.
02 — The Transfer Map
What Moves Directly vs What Gets Rewritten
Every mobile asset falls into one of four categories. Knowing this prevents wasted Jules tasks.
Mobile Asset Transfer Type Web Equivalent Who Does It
packages/shared/data/* ✓ Direct reuse Same import, same package Already done
locales/*.json (AR/EN strings) ✓ Direct reuse Copy into messages/, adapt to next-intl / i18next Jules task
theme/ design tokens ~ Adapt Convert to CSS variables in web Tailwind config Jules task
docs/design-system.md ✓ Direct reuse Reference doc — same design language on web You reference it
state/ (Zustand stores) ~ Adapt Same Zustand stores work in browser — minor adjustments (no AsyncStorage) Jules task
screens/ logic (non-UI) ~ Adapt Extract business logic → hooks; rebuild UI in React + Tailwind Jules task
components/ React Native UI ✗ Rewrite New web components using shadcn + Tailwind (same design language) Jules task
React Navigation (mobile routing) ✗ Replace React Router v6 / TanStack Router with URL-based routes Jules task
Arabic text rendering / RTL ⚠ Critical dir="rtl" on HTML + font-arabic class. Must be set up in Sprint 1 globally. Jules task S1
Audio / TTS (if any) ~ Adapt Web Audio API / Howler.js instead of Expo AV Jules task
docs/notebooklm/** chapters ✓ Direct reuse Same content, rendered via shared package Already done
Drizzle schema (web already has config) ✓ Ready Define tables for progress, user, session tracking Jules task S1
⚠️ Arabic RTL is non-negotiable in Sprint 1. If you build even 5 components without RTL configured globally, you'll have to retrofit every single one. Set dir="rtl", Arabic font, and Tailwind RTL plugin in the very first Jules task before anything visual is built.

04 — The Master Plan
Sprint-by-Sprint Breakdown
Six sprints to get from scaffold to feature-complete web app. Each sprint runs as a parallel Jules batch. Foundation first — always.
Sprint Theme Issues to Generate Jules Tasks
S1 Foundation
No UI yet — infrastructure only
  • RTL + Arabic font global setup (html dir, Tailwind RTL plugin)
  • i18n setup — copy locales/, wire up web messages/
  • Design tokens → web Tailwind config (from mobile theme/)
  • Drizzle schema: users, progress, sessions, bookmarks
  • Routing skeleton: React Router v6 + layout components
  • shared package import verification in web
 6 tasks
S2 Core UI Components
Web component library
  • ArabicText component (RTL, font, diacritics, size variants)
  • ProgressBar component (matches mobile design)
  • LessonCard component
  • NavigationSidebar / mobile nav
  • Button, Input, Modal (from shadcn + design-system.md)
  • AudioPlayer component (Howler.js, matches mobile audio UX)
  • ChapterBadge / level indicator
 7 tasks
S3 Core Screens: Learning
Port mobile screens as web pages
  • Home / Dashboard page (progress overview)
  • Chapter list page (all volumes + chapters)
  • Lesson page — chapter reading view
  • Vocabulary page (word list, search, filter)
  • Exercise page (exercises from shared/data)
  • Progress/Stats page
 6 tasks
S4 Pedagogical Engine
The Arabic learning logic
  • Zustand state: port mobile state/ stores to web
  • Spaced repetition / review scheduler
  • Morphology / grammar analysis display
  • Translation toggle (AR ↔ EN)
  • Search across all Arabic content
  • Bookmarks — persist to Drizzle
  • User progress persistence (Drizzle)
 7 tasks
S5 Polish + Web-Specific
Features native to web
  • Keyboard shortcuts (j/k navigation, space for audio)
  • Print / PDF export of lessons
  • URL deep-linking (share exact lesson/word)
  • Dark mode toggle (design-system.md dark palette)
  • Responsive: tablet + desktop layout variants
  • PWA manifest + offline support
 6 tasks
S6 QA + Launch
Hardening and deploy
  • Smoke tests for all critical user flows
  • RTL audit — verify every screen renders correctly
  • Performance: bundle analysis + code splitting
  • Security review (run security-review.md)
  • CI/CD pipeline + deploy config
 5 tasks
💡 With 100 Jules tasks/day: Each sprint above is one batch. You could theoretically run S1 on Monday morning and be on S4 by Wednesday. In practice, plan 1 sprint per day — review and audit time is the bottleneck, not Jules execution time.

1
🧠 Morning — Prime Your Local IDE

Load project context before any planning

Your IDE has no memory. Every session starts with prime.md to reload full project context.

# In your local IDE (Cursor / Windsurf / Copilot / VS Code): # Open .claude/commands/prime.md and run it as a prompt. # It tells the IDE: your stack, file structure, design system, conventions. # For a sprint focused on UI components, also run: # .claude/commands/prime-client.md (frontend context) # For a sprint focused on API/DB work, also run: # .claude/commands/prime-server.md (backend context) # Tip: Include this in your prime prompt for every sprint: # "Also read docs/design-system.md and docs/theming.md"
2
📄 PRD — Describe This Sprint's Goal

Run create-prd.md → save to .agents/PRDs/sprint-N.md

Even for web porting work, write a PRD. It grounds every plan Jules follows and prevents scope drift.

# Run .claude/commands/create-prd.md in your IDE # Append your sprint goal, e.g. for Sprint 2: "Build the web UI component library for the Arabic learning app. Reference: docs/design-system.md, mobile app components/ folder. Web stack: React + Vite + Tailwind + shadcn/ui. RTL is already configured globally (Sprint 1 done). Components needed: ArabicText, ProgressBar, LessonCard, NavigationSidebar, AudioPlayer, Button, Modal variants. Each component must have: TypeScript types, RTL support, dark mode support, storybook-style usage comment." # Output lands in .agents/PRDs/sprint-2-components.md # Review it — if anything looks wrong, edit the text now.
3
🎫 Issues — PRD → GitHub Backlog

Run create-stories.md → execute the batch script

One GitHub issue per Jules task. Each issue must be independently completable — no implicit dependencies.

# Run .claude/commands/create-stories.md in your IDE # It reads the PRD and outputs a shell script # Output: .agents/stories/create-sprint-2-issues.sh # Review the script — check each issue: # ✓ Self-contained (Jules can do it alone) # ✓ References the right files to create/modify # ✓ Includes link to design-system.md in body # ✓ Has acceptance criteria Jules can verify chmod +x .agents/stories/create-sprint-2-issues.sh bash .agents/stories/create-sprint-2-issues.sh # Verify issues in GitHub: gh issue list --label sprint-2 # Create this sprint's integration branch: git checkout integration-sprint-1 # base from previous sprint git checkout -b integration-sprint-2 git push -u origin integration-sprint-2
4
🗺️ Plans — The Most Important Step

Run plan.md for each issue → commit docs/plans/

The plan file is what Jules reads. It must be precise, include mobile reference paths, and list exact files to create or modify. This is where you transfer mobile knowledge to Jules.

For each issue, run .claude/commands/plan.md in your IDE. Add this to the prompt so the IDE knows where the mobile reference lives:

# Prompt addition for every plan.md call on this project: "Reference implementation: apps/mobile/components/[ComponentName] Design tokens source: apps/mobile/theme/ Shared data: packages/shared/data/ Design system: docs/design-system.md Existing mobile state: apps/mobile/state/ The web version uses: React + Vite + Tailwind + shadcn + Drizzle" # Output: docs/plans/issue-23-plan.md # Required sections in every plan: # ✓ Issue number + title # ✓ Branch: feat/issue-23 # ✓ Base branch: integration-sprint-2 # ✓ Files to CREATE (with full paths) # ✓ Files to MODIFY (with full paths) # ✓ Files NOT to touch # ✓ Mobile reference: apps/mobile/components/X.tsx # ✓ Logic to implement (step-by-step) # ✓ Validation commands # After all plans are written — FILE CONFLICT CHECK: # Grep all plans for file names — no two plans in this batch # should list the same file under "Files to modify" grep -h "Files to modify" -A 10 docs/plans/issue-*.md | sort | uniq -d # Push plans to GitHub (Jules reads from the repo): git add docs/plans/ git commit -m "plans: sprint-2 component issues" git push origin integration-sprint-2
5
🚀 Trigger Jules — Fire All Agents

Send all issues to Jules API simultaneously

Jules clones your repo, reads the plan, implements, runs validations, opens PR. You do nothing during execution.

# Jules task prompt template (paste this for each issue, change the number): "Read docs/plans/issue-23-plan.md and implement it exactly. Follow all rules in AGENTS.md. Read docs/design-system.md before writing any UI code. Branch from integration-sprint-2, branch name feat/issue-23. Run all validation commands before opening PR. Open PR to integration-sprint-2 when complete." # Jules UI: jules.google.com → New Task × N (one per issue) # Or via API (if you have a trigger script from scripts/): curl -X POST https://jules.google.com/api/v1/tasks \ -H "Authorization: Bearer $JULES_API_KEY" \ -H "Content-Type: application/json" \ -d '{ "prompt": "Read docs/plans/issue-23-plan.md and implement exactly. Follow AGENTS.md. Read docs/design-system.md before UI work. Branch feat/issue-23 from integration-sprint-2. Auto-create PR.", "githubRepoContext": { "repo": "your-org/arabic-app", "startingBranch": "integration-sprint-2", "targetBranch": "feat/issue-23" }, "automationMode": "AUTO_CREATE_PR" }' # Fire all N tasks. Go have coffee. Jules runs in parallel. # Average Jules execution time per task: 5–20 minutes.
6
🌳 Worktree Review — No Branch Switching

Add worktrees for Jules PRs → review locally

Jules opens PRs. You add a worktree per branch, open it in your IDE, check it runs correctly, especially RTL and Arabic rendering.

# Fetch all Jules branches: git fetch --all # Add a worktree for each Jules PR you want to inspect locally: git worktree add ../arabic-app-wt/feat-issue-23 feat/issue-23 git worktree add ../arabic-app-wt/feat-issue-24 feat/issue-24 # Check a PR (never switches your main folder's branch): cd ../arabic-app-wt/feat-issue-23 pnpm install && pnpm --filter web dev # Arabic-specific review checklist per PR: # ✓ Arabic text renders correctly with proper font # ✓ Layout flows right-to-left visually # ✓ No hardcoded Arabic strings (all via t()) # ✓ Component matches mobile visual reference # ✓ TypeScript has no errors # Run .claude/commands/review.md prompt in the worktree folder # for AI-assisted diff review against the PRD # Remove worktree after merge: git worktree remove ../arabic-app-wt/feat-issue-23
7
✅ Merge — Gated, In Order

CI green → merge → smoke test every 5

Never batch-merge everything at once. Gate every 5 with your smoke.ts script.

# See all PR statuses: gh pr list --base integration-sprint-2 # Merge a passing PR: gh pr merge [PR_NUMBER] --squash --delete-branch # Every 5 merges — run smoke test on integration branch: cd ../arabic-app-wt/integration-sprint-2 git pull origin integration-sprint-2 pnpm --filter web run build # Vite build must succeed pnpm run scripts/smoke.ts # your existing smoke script # CI failing? Send Jules the error: "The CI failed on feat/issue-23. Error: [paste GitHub Actions output]. Fix the issue, re-run all validation commands, push the fix." # Merge conflict? Send Jules: "Pull latest integration-sprint-2, resolve all conflicts, re-run validation commands, push the update."
8
🔄 Sprint Close — Audit + Next Sprint

validate.md → update AGENTS.md → next integration branch

Run the audit, capture systemic mistakes, strengthen AGENTS.md, and prep the next sprint branch.

# Full validation on the integration branch: cd ../arabic-app-wt/integration-sprint-2 # Run .claude/commands/validate.md prompt # Run .claude/commands/review.md prompt (compares vs PRD) # RTL audit (critical for Arabic app): # Open the web app in browser — flip to Arabic mode # Check every new screen/component renders correctly RTL # Capture systemic Jules mistakes → update AGENTS.md # Examples for Arabic apps: # "Jules used dir='rtl' on div instead of html root → add rule" # "Jules hardcoded Arabic string instead of using t() → add rule" # "Jules used LTR margin instead of RTL margin → add rule" # Teardown sprint worktrees: bash scripts/worktree-teardown.sh # Prep next sprint: git checkout integration-sprint-2 git checkout -b integration-sprint-3 git push -u origin integration-sprint-3 # Update INTEGRATION_BRANCH in worktree-setup.sh → sprint-3 bash scripts/worktree-setup.sh
🕌 Arabic-specific AGENTS.md rules to add as you go: Every time Jules gets RTL wrong, renders Arabic text without diacritics support, uses a hardcoded string, or imports from the wrong i18n key path — add a precise rule. After 3 sprints, Jules will produce near-perfect Arabic components automatically.
